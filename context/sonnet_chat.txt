O problema central do multiplatform com Vulkan
Vulkan não roda nativamente no macOS — você já está desenvolvendo no Mac. O MoltenVK é uma implementação do Vulkan que traduz chamadas Vulkan para o Metal da Apple, permitindo que apps Vulkan rodem em macOS, iOS e tvOS. 
GitHub
 Isso tem implicações profundas na arquitetura desde o dia 1.

O modelo recomendado é usar a biblioteca dinâmica do MoltenVK em conjunto com o Vulkan Loader — nesse cenário o MoltenVK assume o papel de ICD do ponto de vista da aplicação, e você linka apenas ao Vulkan Loader, não ao MoltenVK diretamente. 
Lunarg

A consequência disso é que a arquitetura precisa de uma camada de capacidades que negocia o que o dispositivo atual suporta — em vez de assumir features.

O que mudou em relação ao plano original e por quê
A maior mudança é a camada RHI. O plano original expunha VkHandle direto nas camadas superiores — isso é um problema para multiplatform porque torna impossível testar o GS-VM sem GPU, e amarra o GS-VM ao Vulkan para sempre. A solução é inserir uma RHI (Rendering Hardware Interface) com interfaces puras C++ entre o GS-VM e o backend Vulkan. O GS-VM fala com ITexture, ICommandBuffer, nunca com VkImage ou VkCommandBuffer.

O CapabilityNegotiator é crítico para sua situação específica. Você está desenvolvendo no Mac com MoltenVK. O MoltenVK agora suporta Vulkan 1.4 como portability subset desde agosto de 2025, incluindo VK_KHR_dynamic_rendering e extended dynamic state. 
Grokipedia
 Mas VK_EXT_attachment_feedback_loop_layout — que você precisa para o GS feedback loop — pode ou não estar disponível. O CapabilityNegotiator decide em runtime qual caminho tomar: Input Attachments (preferido) ou Compute + Storage Images (fallback), sem que o código de cima precise saber.

A extensão VK_KHR_portability_subset é obrigatória no macOS. A Vulkan Portability Initiative padroniza queries para funcionalidades disponíveis em implementações em camadas como o MoltenVK, e a extensão VK_KHR_portability_subset permite que essas funcionalidades sejam testadas por conformidade. 
Vulkan
 Seu ExtensionManager precisa ativá-la automaticamente quando detectar que está rodando sobre Metal.

O Null Backend não é frescura. Ele permite testar todo o pipeline de swizzling do GS-VM, decodificação de .bin, e a lógica dos 5 passes sem precisar de GPU — isso é fundamental para CI headless e para debugar a lógica PS2 isolada da complexidade Vulkan.

As 4 regras de ouro que guiam cada decisão de código
Query first — antes de usar qualquer extensão ou feature, consulte VkPhysicalDeviceFeatures2 via pNext chain. Nenhum if (platform == macOS) no código — só if (caps.hasFeedbackLoop).

Zero leakage — nenhum VkHandle sobe além do Vulkan backend. O RHI retorna handles opacos uint32_t ou std::shared_ptr<ITexture>. Isso é o que permite o Null Backend existir.

Pipeline cache — sempre serializar o VkPipelineCache em disco entre execuções. Compilar SPIR-V para código de máquina é lento; no macOS com MoltenVK também envolve transpilação para MSL. O cache elimina isso em runs subsequentes.

VK_KHR_synchronization2 — usar a API moderna de sync desde o início. A API velha (vkCmdPipelineBarrier com srcStageMask / dstStageMask separados) é mais propensa a erros e já está de facto deprecated nos drivers modernos.

A próxima sessão sobre multiplatform vai fundo no CapabilityNegotiator e no ExtensionManager — esses dois juntos são o coração da portabilidade. Essa é a questão central do projeto. Deixa eu ser preciso:

O que o PS2 GS faz de verdade
O GS não tem essa restrição do OpenGL. Ele tem uma VRAM unificada e o rasterizador pode ler e escrever no mesmo endereço de framebuffer no mesmo frame — pixel a pixel, durante a rasterização. É isso que cria a refração: o cristal lê o pixel de fundo enquanto está sendo desenhado em cima dele.

Por que o OpenGL proíbe isso
É undefined behavior na spec. O driver não tem garantia de quando o write vai chegar ao cache vs quando o read vai buscar — então o resultado é não-determinístico. Alguns drivers dão resultado errado silenciosamente, outros corrompem completamente.

Como o Vulkan resolve — e qual nível de fidelidade cada abordagem dá
Abordagem	Fidelidade	Observação
VK_KHR_dynamic_rendering_local_read	100%	Lê o tile memory do pixel exato em rasterização
VK_EXT_attachment_feedback_loop_layout	~95%	Lê do framebuffer mas com custo de flush de cache
Cópia de framebuffer antes do draw	~80%	Lê frame anterior, não o pixel atual
Compute + barrier explícita	~95%	Correto mas overhead de sync
O local_read é a única abordagem que replica exatamente o comportamento do GS, porque:

glsl
// gs_crystal.frag — isso é o que o PS2 faz nativamente
layout(location = 0) tileImageEXT highp iimage2D colorTileImage;

void main() {
    // lê o pixel EXATO que está sendo rasterizado agora
    // não uma cópia, não o frame anterior — o pixel atual
    vec4 background = imageLoad(colorTileImage, ivec2(gl_FragCoord.xy));
    vec2 refractedUV = screenUV + normalScreen;
    fragColor = texture(crystalTex, refractedUV) * background;
}
O detalhe que importa para você
No macOS com Apple Silicon, esse caminho é literalmente gratuito em performance — o M1/M2/M3 é tile-based deferred rendering (TBDR), exatamente como o PS2. O local_read mapeia direto para o tile memory do Metal. Você está desenvolvendo na plataforma onde essa feature é nativa.

Em desktop (PC), o mesmo código funciona mas o driver emula o tile access com um flush — há um custo pequeno, mas o resultado é idêntico.

Conclusão
Não tem impedimento — pelo contrário. O VK_KHR_dynamic_rendering_local_read que o Gemini sugeriu é exatamente a solução correta para fidelidade 100%, e a única razão para ter o fallback no CapabilityNegotiator é hardware muito antigo. No seu Mac com Apple Silicon você já tem o caminho ideal.

A única ressalva: confirmar que VK_KHR_dynamic_rendering_local_read está presente via query antes de usar — o que o CapabilityNegotiator faz automaticamente.

Agora o raciocínio por trás de cada decisão:

Por que cada abstração existe
VulkanContext é a única classe que faz bootstrap (via vk-bootstrap) e owna VkDevice, VkQueue e VkSurfaceKHR. Toda outra classe recebe uma const VulkanContext& — nunca copia handles, nunca cria device. Isso elimina o problema clássico de "quem destrói o device primeiro".

ResourceManager + VMA resolve o problema central de memória. Em vez de chamar vkAllocateMemory para cada buffer/imagem (o Vulkan Guide avisa que isso quebra em drivers que limitam o número de allocations), o VMA gerencia um heap único e faz sub-alocação. As structs AllocatedBuffer e AllocatedImage são simples pairs de {VkBuffer/VkImage, VmaAllocation} — sem herança, sem virtual.

FrameData[×2] é o padrão frames-in-flight da doc oficial. Você mantém 2 conjuntos de {VkCommandBuffer, VkSemaphore acquire, VkSemaphore render, VkFence} e alterna entre eles. A GPU processa o frame N enquanto a CPU grava o frame N+1 — sem stall.

PassRecorder é a abstração mais importante e mais fina. Ela wrapa vkCmdBeginRendering / vkCmdEndRendering do Vulkan 1.3 Dynamic Rendering, e toda transição de layout de imagem passa por ela via vkCmdPipelineBarrier2 do sync2. A regra: nenhum vkCmd* existe fora do PassRecorder. Isso garante que cada pass no RenderDoc tem um label limpo e todas as barriers estão no lugar certo.

DeletionQueue é um std::deque<std::function<void()>>. Quando você cria qualquer recurso Vulkan, empurra o destrutor na fila. No flush() você executa tudo em ordem reversa. Resolve o problema de lifetime sem precisar rastrear dependências manualmente.

PipelineBuilder usa builder pattern pra isso:

cpp
// ao invés de preencher 400 linhas de VkGraphicsPipelineCreateInfo
auto pipeline = PipelineBuilder{}
    .setShaders(vertSpv, fragSpv)
    .setColorFormat(VK_FORMAT_B8G8R8A8_UNORM)
    .setBlendMode(BlendMode::Additive)        // pra os passes Edge/Offset do GS
    .setPushConstantSize(sizeof(GsSpritePush))
    .build(ctx, shaderLoader);
GS-VM sem Vulkan — o SwizzleEngine retorna std::vector<uint8_t>. O ResourceManager recebe esse vector e faz o upload via staging buffer. Os dois módulos nunca se tocam diretamente. Isso significa que você pode testar o decode de qualquer .bin com um main.cpp de 10 linhas sem subir Vulkan.

Push Constants pra dados per-draw — o Vulkan Guide é claro: push constants são a forma mais rápida de passar dados pequenos (até 128 bytes garantidos em qualquer driver) para o shader, sem descriptor sets. Para os 5 passes do GS, cada draw vai ter uma struct:

cpp
struct GsSpritePush {
    glm::vec2 uvOffset;    // screenUV + normalScreen
    float     rodScale;    // (1A - idx) / 5.0
    uint32_t  texVramAddr; // endereço na VRAM virtual
};
// vkCmdPushConstants — zero overhead de descriptor update

void RenderOrchestrator::drawFrame() {
    auto& frame = frameData[currentFrame % 2];
    
    vkWaitForFences(device, 1, &frame.fence, VK_TRUE, UINT64_MAX);
    swapchain.acquireNextImage(frame.acquireSemaphore);
    vkResetFences(device, 1, &frame.fence);
    
    frame.cmdPool.reset();
    auto rec = PassRecorder{frame.cmd};
    
    rec.transitionToColorAttachment(swapchain.currentImage());
    rec.beginRendering(swapchain.currentImageView(), extent);
        gsBaseRefractionPass(rec);   // bind local_read pipeline
        gsEdgeAdditivePass(rec);
        gsOffsetAdditivePass(rec);
        gsSelectedRefractionPass(rec);
        gsSelectedFillPass(rec);
    rec.endRendering();
    rec.transitionToPresent(swapchain.currentImage());
    
    swapchain.present(frame.renderSemaphore, frame.fence);
    deletionQueue.flush();  // limpa recursos do frame anterior
}

Cara, isso é uma mina de ouro. Dá pra extrair informação cirúrgica daqui. Deixa eu mapear o que já existe para a arquitetura Vulkan:

O que o código revela de preciso
Os 5 passes estão implementados com blend factors OpenGL explícitos. Isso é o mapeamento direto para VkPipelineColorBlendAttachmentState:

Pass 1 — GL_SRC_ALPHA / GL_ONE_MINUS_SRC_ALPHA  →  VK_BLEND_FACTOR_SRC_ALPHA / DST_ALPHA
Pass 2 — GL_ONE / GL_ONE                         →  VK_BLEND_FACTOR_ONE / ONE  (additive)
Pass 3 — igual pass 2 + offset matrix            →  mesmo pipeline, push constant diferente
Pass 4 — igual pass 1, só rod 0                  →  mesmo pipeline do pass 1
Pass 5 — GL_ONE_MINUS_SRC_ALPHA / GL_SRC_ALPHA   →  reverse alpha — pipeline próprio
Ou seja: você precisa de 3 pipelines Vulkan distintos, não 5. Passes 1/4 compartilham um, 2/3 compartilham outro, pass 5 é único.

O feedback do tunnel já está lá — e mostra exatamente o problema:

cpp
// linha crítica — lê a tunnelLayer COMPLETA antes de desenhar os cristais
prism.materials[0].maps[MATERIAL_MAP_EMISSION].texture = tunnelLayer.texture;
Isso é leitura do frame anterior do tunnel — não do pixel simultâneo. É por isso que fica 45%. Com local_read você lê o pixel exato durante a rasterização do cristal, dentro do mesmo render pass.

Os uniforms que viram push constants:

cpp
// Raylib (uniforms caros, por draw call)
SetShaderValue(crystalShader, locRenderPass, &pass,  SHADER_UNIFORM_INT);
SetShaderValue(crystalShader, locRodAlpha,   &alpha, SHADER_UNIFORM_FLOAT);
SetShaderValueMatrix(crystalShader, locModel,   finalModel);

No Vulkan isso vira uma struct de push constants — zero overhead:

cpp
struct CrystalPush {
    glm::mat4 model;      // 64 bytes
    glm::mat4 mNormal;    // 64 bytes
    int32_t   renderPass; //  4 bytes
    float     rodAlpha;   //  4 bytes
    glm::vec2 _pad;       //  8 bytes
};                        // = 144 bytes (dentro do limite de 128 garantido... quase)
Hmm — 144 bytes estoura o mínimo garantido. Solução: mNormal não precisa ser mat4 completa, pode ser mat3 empacotada em 3×vec4 = 48 bytes → total 132 bytes. Ainda estoura levemente. Melhor abordagem: model e mNormal ficam num UBO por objeto, só renderPass e rodAlpha como push constants (8 bytes). Limpo e dentro do spec.

GenCrystalRodMesh já é procedural — não precisa de .obj. Porta diretamente para um VkBuffer de vértices no ResourceManager. A geometria está correta: 6 lados, bevel em Y=9.85, taper de 0.866 → 0.766.

BuildRodMatrix e BuildRodMatrixOffset — pure math, zero dependência de Raylib exceto pelo Matrix type. Portam direto com glm::mat4.

Pass 3 desabilitado — o shimmer offset está comentado exatamente porque sem os dados reais do PS2 (param_2[0x2C], param_2[0x2D]) o offset angle é uma estimativa. Esse é o dado que você vai precisar extrair do Ghidra para completar.

O tunnel shader — o efeito de tubo com noiseTexture está lá mas a leitura do background pelos cristais é frame-delayed. Com local_read isso se resolve estruturalmente.

FXAA — vira um compute pass final ou um fragment shader sobre a swapchain image. Simples de portar.
